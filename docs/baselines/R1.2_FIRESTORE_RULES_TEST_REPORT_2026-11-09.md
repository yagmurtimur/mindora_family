## Automated coverage encoded

The test suite encodes the required authorization cases:

1. Unauthenticated reads and lists are denied.
2. An unrelated parent cannot read child data.
3. A parent is denied before an accepted membership exists.
4. An accepted parent gets only scope-permitted reads.
5. A revocation marker denies even a stale guardian membership.
6. A child cannot change their role or another account.
7. A child cannot self-assign a parent / fabricate either membership mirror.
8. A parent cannot fabricate membership or modify a different child's policy.
9. Multiple children can be listed through the parent’s own deterministic path.
10. A child identity cannot access or register another child's device.
11. Invalid profile/mood fields and types are denied.
12. A parent-side listing mirror without the child-side guardian mirror grants
    no child-data access.

## Security decisions implemented in rules

- All paths are denied unless an explicit allow statement matches.
- `children/{childId}/guardians/{parentUid}` is checked by deterministic
  `exists()`/`get()` for parent access. The rule also requires matching path
  fields, `status == "accepted"`, a requested scope, and no deterministic
  `guardianRevocations/{parentUid}` document.
- `parents/{parentUid}/children/{childId}` is readable/listable only by the
  named parent. It is a listing projection and never grants child-resource
  access.
- Guardian, parent-listing, revocation, invitation, relationship, device,
  analysis, notification-endpoint, aggregate, and policy writes are denied to
  every client. They await R1.3 trusted backend operations.
- Account role/status/lifecycle fields are immutable to clients. Existing users
  may only update safe account preferences.
- Current legacy `users/**` documents are fail-closed. This prevents unsafe
  legacy authorization from bridging into v2, but means the present Flutter
  client cannot work against a deployed version of these rules until the planned
  migration and R1.4 client refactor are complete.

## Unresolved limitations

1. All 13 Firestore Rules tests passed locally. The Firebase CLI returned
   exit code 2 after the test script exited successfully (code 0), due to a
   timeout during emulator shutdown. No emulator process remained afterward.
2. Firestore rules cannot implement trusted invitation acceptance, cryptographic
   token verification, atomic relationship/mirror lifecycle, rate limiting,
   device challenge/attestation, aggregation, notification sending, deletion,
   or reconciliation. These require R1.3 backend work.
3. Rules cannot prove a physical device is Device Owner/Profile Owner or that
   iOS Screen Time enforcement exists. Device documents are not enforcement
   proof.
4. The document cannot verify unknown deployed production rules/indexes; no
   production configuration or data was accessed.
5. Exact retention, guardian/legal consent, final scope grants, device
   attestation, and approved backend identity remain R1.1 unresolved decisions.
